DFlash block size 实验

Qwen3-8B 固定 b16 权重：五种推理长度、五个数据集、75 次正式测量

摘要

本实验固定 Qwen3-8B target 和按 block size 16 训练的 DFlash drafter 权重，只在推理时把 block size 改为 4、8、16、24、32，比较 acceptance、吞吐和相对逐 token AR baseline 的 speedup。五个数据集、每点三次重复，共 75 次正式 invocation 全部成功。

五个数据集的吞吐与 speedup 都在训练匹配的 block size 16 达到最高。跨数据集等权平均 speedup 为 4.198×；扩大到 24/32 后分别降至 4.007×/3.883×。更长 proposal 的新增位置接受率下降且 verification 成本增加，因此固定 b16 权重没有从更长 block 获益。

1. 问题与结论

当前 Transformers 实现允许用 --block-size 覆盖 checkpoint 配置，不修改权重即可运行不同 block size。但 checkpoint 只按 block 16 训练，所以 4/8/24/32 都是固定权重的 OOD 推理长度。

  1. 运行时 block size 技术上可调，五个扫描值均通过 smoke 和正式矩阵。
  2. 当前 checkpoint 的推荐值仍为 16；它在全部五个数据集上均为吞吐和 speedup 最优。
  3. 该实验不能回答“重新训练不同 block size 后哪一个最好”；它只衡量 b16 权重的运行时外推。

3. 代码实现

实验没有修改 DFlash 核心代码。官方 benchmark.py 读取 --block-size，并把它传入 dflash_generate()；生成器构造指定长度的 draft block、执行 target verification，然后提交接受的 draft 前缀和一个 target bonus token。

3.1 Runner 与并行调度

  1. run_benchmark.py 设置可见 GPU，以模块方式调用官方 benchmark。
  2. 每个点独立保存 stdout、stderr、精确命令、参数、GPU、返回码和 wall time。
  3. 只有返回码为 0 才创建 SUCCESS；失败写入 FAILED。
  4. run_sweep.sh 默认跳过已有成功点，以两个 worker 并行处理互斥的数据集分片。
CUDA_VISIBLE_DEVICES=<gpu> /root/miniconda3/bin/python -m dflash.benchmark \
  --backend transformers \
  --model /cephfs/shared/model/Qwen3-8B \
  --draft-model /cephfs/shared/model/drafters/Qwen3-8B-DFlash-b16 \
  --dataset <dataset> --block-size <4|8|16|24|32> \
  --max-samples 32 --max-new-tokens 256 --temperature 0.0

3.2 数据汇总

collect_results.py 不以“发现多少算多少”的方式聚合，而是枚举预期的 75 个点，核验成功标记、返回码、目录/元数据一致性、全部指标和 histogram。它支持多行 histogram，生成 75 行逐 trial 明细和 25 行 mean/SD 聚合表。旧版 collector 只能解析单行 histogram；本次修正仅重建汇总，不改动原始测量。

4. 指标口径

指标定义
Throughput先对 response 的 time-per-output-token 求平均，再取倒数，单位 tok/s
Speedup同一 invocation 内 AR baseline TPOT / DFlash TPOT
tau每轮平均提交 token 数 = accepted draft tokens + 1 个 target bonus token
Draft 接受率(tau − 1) / (block size − 1)

每次 invocation 内 baseline 与候选共享模型、prompt、GPU 和生成参数，因此 speedup 可直接比较。stdout 指标只有两位小数，所有派生值均继承该舍入误差。

block 4→16 时，提交长度与吞吐同步增长；超过 16 后，所有数据集的 tau 都回落。Draft 接受率随 block size 单调下降，例如 GSM8K 从 74.0% 降至 14.8%，MT-Bench 从 52.7% 降至 9.3%。新增 proposal 位置大多没有被接受，却仍消耗 draft 与 verification 计算，解释了 24/32 的性能回落。

6. 异常、失败与限制

  1. Smoke 的 block 4/8 首次因数据缓存缺失且网络不可达失败；缓存就绪后重试成功。残留 FAILED 与最终 SUCCESS 均保留，正式矩阵没有失败。
  2. 没有独立 warmup；每个 invocation 重新加载模型并运行 baseline。三次重复方差较小，但绝对吞吐不是隔离单卡峰值。
  3. 两张 GPU 并行运行不同数据集，会共享 CPU、存储及 PCIe 环境；paired speedup 仍在同一 invocation 内计算。
  4. stdout 只输出两位小数，所以 tau 的 0.00 标准差不表示底层统计逐位相同。
  5. 模型配置文件已记录 SHA256，权重分片和 dataset cache 未逐文件哈希。
