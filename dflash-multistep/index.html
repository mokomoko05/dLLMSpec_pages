摘要

本实验研究 DFlash draft block 在一次 target verification 前执行多次 denoising/refinement，是否能够提高接受长度并降低端到端 decode latency。实验不重新训练 drafter，所有候选 proposal 最终仍由 target 并行验证，因此输出保持 lossless。

当前 checkpoint 只按 clean anchor 加全 MASK block 训练。结果表明，zero-shot partial-token refinement 没有带来收益：prefix reveal 和 confidence top-8 都增加 draft 计算，且 GSM8K 上的 tau 下降。后续若继续，应先训练覆盖 partial-mask/timestep 状态的 drafter。

1. 实验设置

每个 speculative round 先由 DFlash 生成最多 15 个 draft token，再由 target 一次性验证。multi-step 只增加 draft denoising 次数，不改变 target verification、接受规则或最终输出。

2. 三个配置的含义

以下三项是最终正式对照中的三个配置。它们共享同一 target、draft checkpoint、prompt 顺序和 verification 逻辑，区别只在 draft block 在 denoising round 内如何构造。

表 1. 三个配置
配置denoise 次数输入构造用途
single/11[anchor, MASK × 15]，一次 forward 后直接得到完整 proposal官方 DFlash baseline
prefix_reveal/22第一轮预测后固定前缀位置，其余位置重新设为 MASK；第二轮只补后缀测试“保护早期高价值 token、重算后缀”
confidence_reveal/2/top82第一轮按每个位置的 max softmax probability 选 top-8 非连续位置锁定，其余 7 个位置 remask测试“锁定高置信 token、让其余位置利用条件信息重算”

2.1 single/1：基线

这是原始 DFlash 行为。anchor 是当前已确认上下文的最后 token；15 个 draft positions 全部填 MASK。draft forward 同时读取 anchor 和 target hidden features，输出 15 个位置的 logits，按 greedy 语义得到 proposal，随后 target 验证。这一配置只有一次 draft forward，成本最低。

2.2 prefix_reveal/2：固定前缀

第一轮仍输入全 MASK block。得到第一轮 token 后，固定 proposal 的前缀位置，例如 block 内较早的若干 token；剩余后缀位置重置为 MASK，进行第二次 draft forward。第二轮看到固定前缀后重新预测后缀，意图是让前缀信息向后传播，同时避免重算前缀。

它是位置连续的 schedule：固定的是从 block 起点开始的 prefix，而不是根据置信度选择的离散位置。由于需要第二次 draft forward，只有当 acceptance 增益足以覆盖额外 draft latency 时才可能加速。

2.3 confidence_reveal/2/top8：锁定高置信位置

第一轮得到 15 个 draft positions 的 logits，计算每个位置的 softmax(logits).max()，在 15 个位置中选出 confidence 最高的 8 个。保留这 8 个位置的 token，把其余 7 个位置设为 MASK；第二轮只重预测这 7 个位置。top-8 不要求位置连续，因此可能同时锁定前缀和后缀位置。

这个策略的假设是：高置信 token 已经足够可靠，锁定它们能给剩余 MASK 位置提供更好的条件；但当前 checkpoint 没有训练过“部分 token 已知、部分 token MASK”的输入分布，所以它属于 zero-shot OOD refinement。

3. 代码实现

实现位于 DFlash 子模块的实验分支 exp/multistep-denoising，confidence 版本 commit 为 c982c1b。根实验记录位于 agentWorkSpace/20260818_dflash_multistep_denoising/，根仓库 main 只同步实验记录，不默认合并实验代码。

3.1 公共生成循环

  1. 在当前 start 位置保存 anchor，并构造 block token：第一轮是 anchor + 全 MASK。
  2. 调用 draft model 的单步 denoise helper 得到 logits、token proposal 和诊断信息。
  3. 如果配置是 single/1，立即结束 denoising；如果是两轮配置，按策略生成下一轮的 partial block。
  4. 每次 draft forward 结束后把 draft KV cache crop 回 start，避免未验证 token 的 KV 泄漏到下一 speculative round。
  5. 完成最终 proposal 后只执行一次 target verification，提交 accepted prefix 加 bonus token。

3.2 策略分支的伪代码

block = [anchor] + [MASK] * draft_len
logits = draft_step(block, target_hidden, first_step=True)
proposal = argmax(logits)

if strategy == "single":
    final = proposal
elif strategy == "prefix_reveal":
    k = schedule(step=1, draft_len=draft_len, steps=2)
    block = [anchor] + proposal[:k] + [MASK] * (draft_len-k)
    logits = draft_step(block, target_hidden=None, first_step=False)
    final = fill_mask_positions(block, argmax(logits))
elif strategy == "confidence_reveal":
    confidence = softmax(logits).max(dim=-1).values
    locked = topk(confidence, k=8).indices
    block = remask_except(proposal, locked)
    logits = draft_step(block, target_hidden=None, first_step=False)
    final = fill_mask_positions(block, argmax(logits))

target_verify(final)

3.3 代码入口

  • scripts/run_multistep_experiment.py：统一 runner，支持 strategy、steps、trial、profile 和诊断输出。
  • scripts/validate_denoise_strategy.py：检查 steps=1 基线、repeat-mask logits/cache、anchor 和边界。
  • scripts/run_confidence_phase0.sh：confidence 单样本机制检查。
  • scripts/run_confidence_phase1_gsm8k.sh：GSM8K paired formal sweep。
  • scripts/profile_multistep.py：CUDA event 与 torch.profiler。

后续 denoise 不再次注入同一份 target hidden context：第一轮写入后只保留已确认历史的 cache，第二轮从当前 start cache 出发。这是 multi-step 实现中最重要的 cache 约束。

因此候选的负结果不是由 cache 位置偏移造成，而是由 partial-token OOD 与额外 draft 计算共同造成。

prefix reveal 的 decode latency 增加约 20.4%，tau 下降约 7.6%；confidence top-8 的 latency 增加约 27.2%，tau 下降约 12.2%。Phase 0 中 confidence tau 曾从 3.667 升至 3.778，但 latency 同时从 12.983 升至 14.741 ms/token，单样本上升不足以改变结论。

6. 结论与后续

  1. DFlash multi-step 的三种正式配置分别代表一次基线、连续前缀 reveal 和离散 confidence reveal。
  2. 代码已正确处理 target hidden context、draft KV cache crop、anchor 固定和单次 target verification。
  3. 当前 checkpoint 上两种 multi-step 候选都降低 acceptance 并增加 decode latency，按 Go/No-Go 规则判定 No-Go。
  4. 这不是对多步 diffusion 的普遍否定；下一步应训练 partial-mask / timestep-aware drafter，再复用同一 runner。
