摘要

为混合 GDN target 的候选树实现按父节点索引执行的原生 CUDA kernel：causal conv 和 gated-delta recurrent state 按深度波次计算，每个 anchor/tree 节点只计算一次，不再把 root-to-leaf 公共前缀重复展开。独占同一 GPU、相同框架 commit 和请求口径的 GSM8K-32 中，CUDA tree 的端到端吞吐为 47.858 tok/s，相比同轮 packed-path tree 的 38.621 tok/s 提升 23.9%；但低于 official DFlash2 的 70.103 tok/s。先前 GPU 占位进程未停止的测试已标为无效，不进入本结果。

一轮只运行一个方法，切换方法时先关闭服务并确认 GPU 无其他 compute process；三组按 official → packed → CUDA 顺序执行。

2. CUDA DAG kernel 与 target 接入

tree 的 anchor 是 row 0，候选节点映射到 row 1…21。每个节点的卷积 rolling state 和 recurrent matrix state 从自己的父节点读取，siblings 相互独立。CUDA launcher 按深度顺序启动 kernel 形成依赖 barrier；conv 每块处理一个节点，recurrent 每个 warp 处理一个 value-head state row，以 float32 更新状态。常规输入投影、post-conv q/k 归一化和门值准备、输出投影与 full-attention ragged kernel 均保持原实现。

旧 packed backend 在同一组树中平均每 GDN 层处理 42.805 个 root-to-leaf path tokens；CUDA backend 只处理 anchor+21 个 unique rows。两者在 48 个 GDN 层上均运行，并仅提交最终 accepted path 的状态。数值单测比较 PyTorch reference 与旧 backend，通过 BF16 输出和 FP32 state 容差；真实服务 trace 确认每 verification step 单次 target forward。

3. GSM8K-32 完整正式结果

从每个请求的 scheduler trace 计算 tau = (accepted_draft_tokens + verification_steps)/verification_steps，再对请求等权平均。吞吐是正式 32 条实际 completion token 总数除以客户端墙钟时间；不包含服务加载和 warmup。

4. 正确性、输出差异与性能边界

三组每组 32/32 请求成功，server 日志没有 ERROR、Traceback、OOM 或 CUDA error，scheduler trace 与请求均可对齐。CUDA 与 packed 的最终文本逐字相同 25/32；差异样本编号 2、12、14、16、24、27、31。样本 14、24 中 packed 达到 512-token 上限，而 CUDA 正常停止并输出 boxed answer；CUDA 总输出因此比 packed 少 169 tokens。浮点累加顺序不同可能改变后续生成轨迹，本结果不声称逐字等价或相同生成工作量；吞吐按事先固定的实际在线请求口径计算。

5. GPU 占位进程管理与原始记录

早期测试错误地保留持续运行 GEMM 的 6.7 GiB GPU0 占位，导致竞争和 OOM；这些测量全部标为无效。本轮于 20:56 CST 停止占位 PID 49236、确认 GPU 空闲后运行三组，21:16 CST 重启占位 PID 53501 并核对显存。复现需使用带独占检查和退出恢复 trap 的 matrix runner，不能直接将旧受争用数字并入结论。
