摘要

ours tree 已真实接入 vLLM target backend：每个 speculative step 只执行一次 target model forward，16 个 full-attention 层各调用一次 ragged FlashAttention，48 个 GDN 层各调用一次 grouped convolution 和一次 varlen fused recurrent kernel。候选树直接使用官方 DFlash2 selector checkpoint 的 edge scores 构建。

GSM8K 前 32 条、greedy、thinking off、concurrency 1 的正式结果中，mean per-request tau 从 6.349 提升到 7.174（+13.0%）；wall throughput 从 70.73 tok/s 降到 39.05 tok/s。工程实现相对上一版 5-wave GDN 已提速 60.7%，但 tree 的额外 target 计算仍超过 acceptance 收益。

official 行使用 vLLM 官方 DFlash2 线性 speculative decoding。ours 与 official 使用相同 target、draft/selector、框架 commit、GPU、数据顺序和请求参数。

2. 构树方法与数据流

  1. 官方 DFlash2 drafter 产生各 slot 的候选 token，官方 selector 输出 predecessor→successor edge scores。
  2. official baseline 沿 edge-score argmax 选择 7-token trunk。ours 完整保护该 trunk，再按累计 path probability best-first 扩展 prefix-closed 分枝。
  3. tree budget 固定为 21 个节点，单节点最多 2 个 child。builder 输出扁平 token、parent index、position、ancestor mask 与 root-to-leaf paths。
  4. selector score 只分配候选预算；最终接受由 target greedy logits 做 exact verification，不由 selector 自行决定。
  5. 验证后只提交 anchor 与最长 target-matching path 的 KV、conv state 和 recurrent state，并返回 bonus token。

因此 ours 使用的是官方 selector checkpoint 产生的真实分数，自研内容是候选预算分配、tree metadata、tree target execution、verification 与状态提交。

3. 单次 target forward 与 packed-path GDN

target runner 将 anchor 与 21 个唯一 tree node 放入一次 flattened forward。full-attention 层通过 ancestor mask 限制每个节点只能读取历史 KV 和自己的祖先链，再把所有 leaf query 打包为每层一次 ragged FlashAttention。

Qwen3.8 的 GDN 同时维护 causal-conv rolling buffer 和 recurrent state，分支存在严格父子依赖。当前实现把所有 root-to-leaf paths 组成一个 varlen batch；共享前缀在 GDN 内重复计算，但整层只发起一次 grouped conv 和一次 fused recurrent kernel。计算后选取重复节点的首次结果，映射回唯一 tree rows。

5. 在线与离线评测流程

5.1 在线

  1. 启动单卡 vLLM server，等待 health check，通过一条不计入结果的 warmup。
  2. 客户端以 concurrency 1 顺序发送 32 条请求，逐条记录 latency、completion token 与 finish reason。
  3. scheduler 按 request ID、逐 verification step 记录 accepted draft tokens；ours 额外记录 tree layout、接受路径和 kernel diagnostics。
  4. 完成一种方法后关闭服务，再启动另一种方法，保证 GPU 不重叠。

5.2 离线

  1. 按 request ID 对齐 HTTP 输出、scheduler trace 与 tree trace，并排除 warmup。
  2. 先计算每个请求的 tau，再汇总 mean、median、p05、p95 与标准差；wall throughput 使用 completion token 总数除以客户端 wall time。
  3. 检查 32/32 完成、输出非空、日志无错误、trace 可配对和每 step 单 target forward。
  4. 原始 JSONL 与日志保存在实验节点；仓库提交逐请求 CSV、汇总 JSON、SHA256 和完整中文报告。

6. 正确性、输出差异与下一步

32/32 请求均成功。official 与 ours 有 21/32 输出逐字一致；双方都生成 boxed answer 的 21 条中，最终答案全部一致。sample 14 中 official 在 396 token 输出 \boxed{60} 并停止，ours 到 512-token length limit，未输出 boxed answer。ragged/tree 执行改变了 BF16 数值顺序，接近的 greedy logits 可能进入不同后续轨迹，因此这里不声称逐 token 完全等价。

当前设施已经足以做有意义的 E2E 测量，也确认了 kernel launch 优化的效果。下一步需要减少 tree budget 与 GDN 展开量，或实现能直接处理共享状态 DAG 的专用 GDN kernel；在这些工作完成前，tau 提升不能表述为服务加速。
