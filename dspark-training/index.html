DSpark 训练实验：从 Smoke 到 30K

Qwen3-8B hidden-state 训练模式、延迟分析与真实 acceptance 评测

实验时间
2026-08-16—17
硬件
4 × NVIDIA A100 80GB
Verifier
Qwen3-8B
状态
已完成

摘要

本实验验证 DSpark 在当前 Speculators 和 vLLM 环境中的在线训练流程，并依次完成 smoke、5K pilot 和 30K × 2 epochs 三个阶段。这里的“在线”是指 draft model 训练时按需从冻结的 Qwen3-8B verifier 获取 hidden states，并不更新 verifier 权重。

工程链路可以稳定运行，但训练指标与真实 serving 结果出现明显错配：从 5K 扩展到 30K 后，validation proxy accept length 从 1.9392 提高到 2.850，真实 HumanEval acceptance length 却从 1.514327 降至 1.381908。因此，当前 validation proxy 不适合用于 checkpoint 选择。在继续扩大数据和训练轮数前，应先统一评测口径并检查训练目标与 serving 分布的差异。

2. 官方 DeepSpec 与 Speculators 实验对比

官方 DeepSpec 的 Qwen3-8B 配置是论文级训练 recipe；本地 Speculators 实验是受 4 卡和存储容量约束的缩小验证。两者复用相同的 DSpark 主体结构，但数据量、epoch、hidden-state 供给方式和有效 global batch 差异很大，因此本地 5K/30K 结果不能当成官方训练的等价复现。

2.1 官方脚本流程

  1. download_and_split.py 下载 Open-PerfectBlend，并按 95/5 划分 train 与 held-out prompts。
  2. generate_train_data.py 通过 OpenAI-compatible server 用 Qwen3-8B 重生成 response；公开 Qwen3 参数为 temperature 0.7、top-p 0.8、top-k 20、max tokens 4096、thinking disabled。
  3. prepare_target_cache.py 离线抽取 5 个 target layers 加 final hidden state；Qwen3-8B 全量 cache 估算约 61 TB。
  4. scripts/train/train.sh 调用 train.py --config config/dspark/dspark_qwen3_8b.py，默认单机 8 卡、global batch 512、10 epochs。

官方仓库公开了配置和数据 pipeline，但没有发布完整 Qwen3-8B 训练数据快照、训练 GPU 型号或 wall time。约 1.35M 和 26,360 steps 是依据公开数据量、95/5 split 与 global batch 512 推导的规模，不是日志实测。

3.1 Smoke

Smoke 使用 4 条本地 ShareGPT 格式对话，其中 3 条训练、1 条验证。GPU 0 运行 verifier，GPU 1 执行单进程训练。最终运行完成 hidden-state 请求、前向与反向传播、一次 optimizer step、验证和 checkpoint 保存。

  • 训练 loss：2.316。
  • 验证 loss：1.365209。
  • 成功运行目录：runs/20260816_175207/。

3.2 5K pilot

Pilot 使用 5,000 条重新生成的 Qwen3-8B 样本，训练一轮，共 1,204 optimizer steps。序列长度为 4096；由于 completion 还会请求一个额外 token，vLLM 的服务上限必须至少设为 4097。

  • 稳态训练速度约 4.1–4.5 秒/step。
  • 在线 hidden-state fetch 约占单步时间的 42%–54%。
  • Validation loss 为 0.7738，proxy accept length 为 1.9392。
  • 真实 HumanEval acceptance length 为 1.514327。

3.3 30K × 2 epochs

30K 实验从 5K 模型权重初始化，但重新初始化 optimizer 和 scheduler。30,000 条样本与 pilot 不重叠，其中 28,500 条用于训练、1,500 条用于验证。两轮共执行 14,425 optimizer steps。

  • 训练主体耗时 13 小时 50 分 40 秒。
  • 包含预处理和两轮评测的端到端耗时为 14 小时 20 分 16 秒。
  • 全程没有 OOM、NaN、NCCL 或 HTTP 错误。
  • Validation 指标继续改善，但两个 epoch 的真实 acceptance 都低于 5K pilot。

4. Online / Offline / Hybrid 训练与评测流程

三种模式训练同一个 DSpark draft model，verifier 始终冻结；区别只在 target hidden states 何时生成、是否保留，以及训练时是否继续依赖 vLLM。

模式Hidden states训练时 vLLM典型参数适用场景
Onlinecache miss 时按需生成，加载后删除必须常驻on-missing=generate
on-generate=delete		磁盘紧张、单轮或快速迭代
Offline训练前由 data_generation_offline.py 全量生成并持久化训练阶段可关闭on-missing=error多次复用、追求稳定 step time
Hybrid第一轮按需生成并保留，后续 epoch 直接读 cachecache 完整前常驻on-missing=generate
on-generate=cache		多 epoch，想省去独立预生成阶段

4.1 本次采用的 Online 流程

  1. 准备对话数据，完成 tokenize 和 train / validation split。
  2. 在 GPU 0 启动冻结的 Qwen3-8B vLLM hidden-state server。
  3. GPU 1–3 上的 trainer 为当前样本请求缺失的目标层 hidden states。
  4. vLLM 返回指定层表征；trainer 消费对应文件后立即删除。
  5. DSpark 计算 token CE、TV distribution matching、confidence 和 Markov 相关损失。
  6. 各 DDP rank 完成 optimizer step，按周期执行 validation 并保存 checkpoint。

4.2 Offline 流程

  1. 启动 vLLM hidden-state server，并用 data_generation_offline.py 遍历 prepared dataset。
  2. 将每条样本指定层的表征写入持久 cache，校验样本数、模型、层号和数据 revision。
  3. 停止 verifier，把全部可用 GPU 分配给 trainer。
  4. 训练时只读 cache；缺失立即报错，避免静默混入不同口径的数据。

4.3 Hybrid 流程

  1. 像 Online 一样同时启动 vLLM 与 trainer，但将新生成文件设为保留。
  2. 第一 epoch 逐步填充 cache；命中的样本直接读取，缺失的样本在线生成。
  3. 第二 epoch 起大部分请求转为磁盘读取，训练逐渐接近 Offline。
  4. 确认 cache 完整后，续跑可改成缺失即报错并关闭 vLLM。

4.4 真实 acceptance 评测

  1. 将训练 checkpoint 转换到隔离的 serving 目录。
  2. 使用 vLLM V2 runner 加载 Qwen3-8B target 和 DSpark draft model。
  3. 使用 Speculators evaluator 和 GuideLLM 发送 HumanEval 请求。
  4. 从 serving metrics 汇总 draft 数、accepted tokens 和逐位置接受率。

训练 validation 的 proxy accept length 不经过完整 serving 路径，因此只能视为代理指标，不能代替真实 speculative decoding acceptance。

5. 延迟与资源

表 2. 训练延迟与显存观测
实验稳态 step timeHidden-state fetchVerifier GPUTrainer GPU
5K pilot均值 4.331 s均值 2.147 s约 62.3 GiB观测约 42.6 GiB
30K × 2均值 3.383 s均值 2.000 s约 62.0 GiB每卡约 24.0 GiB

两份原始日志排除首个编译 step 后，有效 tokens/step 几乎相同（3447.4 vs 3444.1），所以 30K 较快不是因为数据规模。总 step time 减少约 0.948 秒，其中 backward 从 1.935 秒降到 1.171 秒，optimizer 从 55.2 ms 降到 30.4 ms，二者贡献约 83% 的缩短；fetch 只减少约 0.148 秒。

代码路径和显存共同指向参数 dtype：5K 从零初始化，fresh model 在 DDP setup 中没有显式转 BF16；checkpoint 保存时权重与 optimizer state 被转换为 BF16。30K 通过 --from-pretrained 从该 BF16 checkpoint 继续训练，因此反向和 optimizer 更轻，trainer 显存也从约 42.6 GiB 降到约 24.0 GiB。这个解释有同机日志和代码支持，但尚未做强制 FP32/BF16 的独立 A/B，因此应视为主因判断，而非最终受控 benchmark。

6.1 HumanEval 评测口径

三组 checkpoint 使用相同本地口径：Speculators evaluator、vLLM V2、GuideLLM 0.7.3、HumanEval 前 80 条、temperature 1.0、最大并发 8、最大输出 4096。

官方 Qwen3-8B DSpark 报告的 acceptance length 为 5.454539，但使用 DeepSpec evaluator、164 条 HumanEval、batch 1 和 non-thinking。两者不是严格同口径，不能直接排名；当前约四倍差距仍表明本地复现尚未对齐。

8. 结论与后续

  1. 在线 hidden-state 生成、训练、验证、checkpoint 转换和 serving 评测链路均已跑通。
  2. 扩大到 30K 数据和两轮训练显著改善离线 validation，但没有提高真实 acceptance。
  3. 当前 validation proxy 不应作为 checkpoint 选择标准。
  4. 下一步应先用官方口径重测三个 checkpoint，再检查 confidence / Markov loss、训练数据生成方式和 evaluator 配置。
  5. 在真实 acceptance 信号稳定前，不建议继续单纯增加数据规模或训练轮数。
