摘要

本实验记录 speculative decoding 的 tree verification 中，target model 产生的 token 为什么没有沿当前已接受前缀被接受。对每个 verification round，只记录第一个真正不匹配的 target token；如果路径走到叶子，target 在叶子之后产生的是 bonus token，不属于被拒绝的 draft token，因而不计入 rejected 分母。

结果显示，六个数据集上最常见的是“target token 在 draft 的位置 top-k 中，但最终树没有把它挂到当前路径”（类别 1.1）。DDTree 还经常出现 token 已在树中但父节点错误（类别 2）；DARTree 的错误父节点比例整体较低，但 Alpaca 上 token 不在 top-k 的比例明显升高。

1. 问题与分类

设当前已确认前缀为 P，当前 round 的树根为 anchor，target verification 从已接受路径的最后节点 p 继续。若 target 在位置 p 给出 token y，但 y 不是 p 的 child，则记录一次 rejected token。令 d(p) 为父节点深度，Cd 为 draft 在对应位置的候选 top-k，Td+1 为最终树在下一深度的节点集合。

1.1: y ∈ Cd 且 y ∉ Td+1（候选有，但树省略）1.2: y ∉ Cd（候选 top-k 未覆盖）2: y ∈ Td+1，但 parent(y) ≠ p（树中存在，父节点错误）

分类优先级为 2 → 1.1 → 1.2：如果同一深度已有相同 token，即使它也在候选 top-k 中，也判为错误父节点，因为此时首要问题是路径挂载位置。统计使用 token id，而非字符串，避免空格和特殊 token 解码造成歧义。

2. 数据流

2.1 位置与深度

generated_position 是相对于回答起点的 0-based 位置：absolute_position − prompt_length。tree_depth 是从树根之后开始计数的 1-based 深度。最后一个候选 block 可能超过请求的最大生成长度，位置不小于 max_new_tokens 的记录已过滤。

3. 代码实现

固定实现位于 dLLMSpec commit c717e5f（分支 exp/dtree-rejected-token-trace-20260904，已推送到 origin）。DDTree 的分类器在 agentWorkSpace/20260826_ddtree_official_reproduction/upstream/ddtree.py，DARTree 的分类器在 agentWorkSpace/20260823_dartree_reproduction/upstream/eval_dartree.py。两处都实现同一优先级和字段 schema。

  1. follow_verified_tree 从 root 逐节点读取 target posterior，返回最长 accepted index path。
  2. classify_rejected_token 读取 accepted path 最后节点，检查 child map、同深度 token、对应 draft candidate top-k，并生成类别。
  3. 每轮 trace 记录 node_token_ids、node_depths、parents 和 accepted_indices，使分类可离线审计。
  4. analyze_rejected_token_trace.py 按 method/dataset、generated position 和 tree depth 计算 count 与百分比。
s(y1:i) = Σj=1…i log softmax(zj)[yj]τ = accepted draft tokens + 1 target bonus（本页不把 τ 当 rejected 分母）percentage(category) = count(category) / Σc∈{1.1,1.2,2} count(c)

其中 zj 是 draft 在第 j 个 slot 的 vocabulary logits。上式的路径分数解释了 DDTree 的 best-first 选择；DARTree 的 path scorer 也使用路径条件进行候选排序，但最终分类只依赖实际构造的 parent/token 关系。

5. 结果解读

5.1 主要瓶颈是树保留和父节点

DDTree 在所有数据集上 1.1 占 59.94%–70.06%，错误父节点占 21.50%–37.18%。这说明 target token 很多时候已经在 draft 的候选 top-k 中，损失来自全局节点预算、best-first 路径选择或分支挂载，而不是 draft 完全没有提出该 token。单纯增大 top-k 对这部分问题帮助有限；应优先分析预算分配和 prefix-consistent parent selection。

5.2 DARTree 减少错误父节点，但不保证候选覆盖

DARTree 的错误父节点比例通常低于 DDTree，例如 GSM8K 为 7.62% 对 31.86%，MATH-500 为 10.36% 对 37.18%。这与 path scorer 显式按路径打分、再进行 supertree pruning 的结构一致：保留下来的节点更少出现明显错误挂载。不过 DARTree 的 1.2 通常高于 DDTree，说明 path selection 改善了路径组织，却不能解决 candidate vocabulary 本身没有 target token 的情况。

5.3 Alpaca 是候选覆盖困难的数据集

Alpaca 的 1.2 比例最高或接近最高：DDTree 17.60%，DARTree 23.79%；而数学和代码数据集的 DDTree 1.2 多数低于 3%。开放式指令回答的 token 分布更分散，固定 candidate top-k 更容易漏掉 target。对 Alpaca 类数据，应单独测试更大的候选词表、按位置自适应的 top-k，或让候选预算随不确定性增加。

5.4 下一步实验

  1. 固定 tree budget，扫描 candidate top-k，观察 1.2 是否转化为 1.1/接受。
  2. 固定 candidate top-k，扫描 DDTree 的节点预算和 DARTree supertree width，观察 1.1 与 2 的变化。
  3. 按 generated position 汇总，区分回答开头的前缀错误和长回答后部的路径漂移。
  4. 把 rejected 分类与真实 EAL（每轮 target 接受长度）配对，判断减少哪一类 mismatch 最能提高最终接受长度。

6. 复现与限制

代码固定 commit 为 c717e5f。在已有本地 Hugging Face 数据集缓存的节点上执行：

export HF_DATASETS_OFFLINE=1
bash agentWorkSpace/20260904_dtree_rejected_token_trace/run_multidataset_trace.sh
python agentWorkSpace/20260904_dtree_rejected_token_trace/analyze_rejected_token_trace.py \
  agentWorkSpace/20260904_dtree_rejected_token_trace/traces/multidataset_8b_32x256/*_ddtree.json \
  agentWorkSpace/20260904_dtree_rejected_token_trace/traces/multidataset_8b_32x256/*_dartree.json \
  --output agentWorkSpace/20260904_dtree_rejected_token_trace/traces/multidataset_8b_32x256/summary.json

本次提交包含聚合 summary，不包含逐轮原始 trace 和日志；原始文件保留在共享盘的同名实验目录。数据集抽样由 loader 先按 seed 0 shuffle，再取前 32 条；AIME25 的数据集总量只有 30 条。统计只分析 greedy（temperature 0）路径，不能直接外推到 sampling decoding。

代码测试为 1 passed。DDTree 和 DARTree 使用不同 drafter 架构和树构造流程，因此表中比例适合分别诊断各自瓶颈，不应被解释为完全控制变量的算法优劣排名。
