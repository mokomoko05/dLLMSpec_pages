摘要

这组实验不是一个单独的新算法，而是一棵按依赖关系展开的系统设计树：先确认 GPU 的 target verification 容量是否随负载变化，再依次尝试把空闲容量用于更深预测、跨卡预取和拒绝后状态回收。为避免把不同口径混在一起，本页对每项实验都明确回答五个问题：实现了什么代码、运行时发生什么、和谁比较、数字如何计算、证据能支持到什么程度。

唯一保留的主线是动态验证预算：18 个“前缀长度 × batch size”状态上，按 5% 延迟平台选择预算，使 target verification 阶段相对固定 B256 平均减少 27.16% 延迟；这还不是端到端加速。其余方案的失败原因也不同：stale second block 缺少新 target feature；跨卡预取猜不中完整下一状态；早层特征替代降低 acceptance；三种回收方案则无法在正确新前缀下保留足够候选质量。

1. 先理解一轮 DARTree

DFlash/DOMINO drafter 不是独立的小语言模型。它读取目标模型已经确认的上下文，并抽取目标模型第 1/9/17/25/33 层的隐藏表示；随后一次并行生成 16 个位置的基础分布。Domino 的 GRU 根据每条具体前缀修正这些并行分布，DARTree 再把多条分支组织成一棵树。

已确认前缀 P，最后词元为 r
        │
        ├─ target 已有 KV cache 与五路 hidden feature
        │
        ▼
DFlash 一次 forward：产生 16 个并行位置 z[0:16]
        │
        ▼
Domino GRU：为不同前缀维护不同状态
        │
        ▼
DARTree 构树（例：construction width W48）
        │
        ▼
剪枝到 verification budget B256
        │
        ▼
target 一次 forward 并行验证根 + 256 个候选
        │
        ▼
只提交连续匹配路径，再提交 target 给出的 bonus token

1.1 一个具体词元例子

草稿树：
            r
          /   \
         A     X
         │     │
         B     Y
        / \
       C   E

target 在 r 后预测 A  → 命中，走到 A
target 在 A 后预测 B  → 命中，走到 B
target 在 B 后预测 D  → B 的子节点只有 C/E，第一次不匹配

本轮提交：A, B, D
其中 A/B 是被接受的 draft，D 是 target bonus token
下一轮真实前缀：P + A + B + D

本页的“单轮接受长度”或 τ 指一次 target verification 让输出前进多少 token，即“连续匹配的 draft token + 最后的 target bonus token”。b16 的上限是 17。所有新方案产生的 token 都只是候选，最终仍在正确 target KV cache 上重新验证，因此不会改变目标模型的采样规则。

1.2 B、W 和 query count

符号含义例子
W构造 supertree 时保留的前沿宽度，影响 proposal 搜索成本W48
B送给 target 的候选节点上限，不包含已知根B256
query count一次 target forward 实际处理的位置数B256 对应 257 queries

4. 算法 1：动态验证预算

4.1 实现的不是“动态控制器”，而是容量测量器

run_capacity_roofline.py 为每个 batch element 建独立 DynamicCache，构造前缀闭合的树 visibility mask，并真实执行完整词表输出和 argmax。对每个前缀长度 L、batch size N 和预算 B 测 target latency。

输入状态 (L, N)
    │
    ├─ sweep B ∈ {16,32,64,128,256,384,512}
    │
    ├─ 每点 warmup 2 次 + CUDA Event 正式测量 7 次
    │
    ▼
Tmin = 该 (L,N) 下所有 B 的最低验证时间
    │
    ▼
选择最大的 B，使 Tverify(B) ≤ 1.05 × Tmin
    │
    ▼
得到“5% 平台容量”；尚未接入在线 DARTree scheduler

4.2 具体例子：前缀 512、batch 4

固定 B256 时，一批要验证 4×257=1028 个 query；容量选择器改为每请求 B64，总 query 为 4×65=260。B64 的验证延迟为 37.909 ms，相对该状态的固定 B256 低 52.46%。减少的是一次 target verification 的 latency，不包含 acceptance 下降后可能增加的轮次。

18 个状态上的 5% 平台容量
前缀长度batch 1batch 2batch 4
128B384B128B64
256–512B256B128B64
2048B128B64B16
4096B128B32B16

4.3 27.16% 的精确定义

对 6 个前缀长度 × 3 个 batch size 的 18 个状态，分别计算

saving(L,N) =
  [Tverify(B256) - Tverify(Bselected)] / Tverify(B256)

18 个 saving 的算术平均为 27.16%，中位数 20.19%，最大 63.70%；14/18 个状态选择的预算小于 B256，3 个等于 B256，1 个选择 B384。这个数字只能写成“target verification phase 平均降时 27.16%”。

端到端 B384 反例说明为什么不能把它叫作加速：B384 相对 B256 接受长度提高 2.81%，但三数据集 TPOT 宏平均反而 +0.93%（更慢）。硬件平台只给预算上界，最终仍要同时优化 acceptance 的边际收益。

5. 算法 2：用 stale target feature 预测第二块

5.1 想法与具体例子

原 b16 树最多向前 16 个 draft 位置。既然 target 验证 257 和 273 queries 都约 38 ms，可以在一条深度 16 叶子后再挂 16 个节点。但第二块本应读取第一块新 token 在 target 第 1/9/17/25/33 层的表示；这些 feature 在验证第一块前还不存在。

第一块真实需要：h_t
第二块真实需要：h_{t+1}, h_{t+2}, ..., h_{t+16}

实现的零阶保持：
ĥ_{t+1}=ĥ_{t+2}=...=ĥ_{t+16}=h_t

例：
原树最高分深度 16 路径 r→A→...→P
复制 branch-local draft KV cache
用 [h_t × 16] 再跑一次 DFlash
得到第二块单链 Q→R→...
挂到 P 后，形成 257+16=273 query 的合并树

5.2 代码流程

select_scored_path_at_depth()
  选最高分深度 16 叶子并恢复父链
        │
zero_order_hold_target_context()
  复制最后一个精确 feature 16 次
        │
build_multiblock_continuation()
  复制 draft cache，第二次 DFlash forward，构造 16 节点链
        │
merge_tree_extension()
  把局部链父索引映射到原 B256 树
        │
verify_multiblock_shadow()
  复制正确 target cache，验证 273-query 合并树
        │
hybrid_extension_acceptance()
  原 B256 路径沿用原判断，只重放新增链，隔离 BF16 shape drift

5.3 数字到底是什么意思

数字分子 / 分母解释
+0.013 token/round三个数据集“在线最高分分支 + stale feature”每轮额外接受数的宏平均；共观察 618 轮是 0.013 个 token，不是 1.3%；几乎没有延长接受路径
-9.61%在原轨迹上加入第二次 draft、构树、273-query verify 后的 accepted-token/ms，相对原 DARTree 的宏平均变化逐轮 shadow 成本估算，不是沿新轨迹重跑的 E2E TPOT
+7.937 token只在原轮已经接受满 17 token 时，事后给出真实分支和精确未来 feature，新增接受数的宏平均oracle 上限；证明深度有价值，失败点是 feature 不可得
+8.89%真实分支、精确 feature、正确触发轮次三项未来信息都已知时的 accepted-token/ms 上限不可部署，只是设计空间上限

273-query verify 与原 B256 verify 基本同速，但第二次 draft 约 5.7 ms、构造/合并约 4.8 ms，额外约 10.5 ms 并不免费。因此该实现否定的是“复制旧 feature 再递归跑同一 b16”这一具体算法，而不是更长预测本身。

6. 算法 3：第 34 层就绪后的跨卡预取

6.1 设想的双卡流程

GPU 0：target 第 1–34 层
           │ 五路 Domino feature 全部就绪
           ├──────────────┐
           │              │
           ▼              ▼
枚举 m 个完整下一状态     GPU 0 继续第 35–36 层 + lm_head
(接受路径 + bonus)        得到真实下一状态
           │              │
           ▼              │
GPU 1 批量预跑 m 份 drafter
           │              │
           └──────┬───────┘
                  ▼
          命中则复用；未命中全部丢弃并重算

这个方案需要三个条件同时成立：A 能用少量假设覆盖真实状态；B target 尾部有足够时间且 drafter 小批量高效；C 或者能更早得到可用 feature，扩大重叠窗口。

6.2 Probe A：完整下一状态预测

代码在第 34 层对 B64 树的 65 个节点保存 logit-lens 分布。enumerate_hypotheses() 沿树累计“继续走某条已有边”的对数概率，并为每个停止节点枚举 bonus token，最后对完整状态 H=(接受路径, bonus) 全局排序。

例：真实结果为
接受路径 r→A→B，bonus=D

假设 1：(r→A→B, bonus=C)  路径对、bonus 错 → 不命中
假设 2：(r→A,   bonus=D)  bonus 对、路径错 → 不命中
假设 3：(r→A→B, bonus=D)  两部分都对       → 命中
保留假设数完整状态命中仅路径命中
top-120.20%25.66%
top-229.16%35.38%
top-437.85%45.61%
top-848.17%56.01%

48.17% 的分母是 1,173 个真实解码轮次；它表示约一半轮次的真实“路径 + bonus”落入 top-8。预设门槛是 top-8 ≥90%。而最值得预取的长接受轮次（τ=13–17）top-8 只有 32.73%，因此扩大 batch 也难解决。

6.3 Probe B：硬件窗口

代码把真实 target tree forward 在第 34 层后切开计时，并单独微基准 batch 1/2/4/8 的“DFlash 主干 + lm_head + top-64”。

测量结果含义
B64 target 尾部2.727 ms / 总 37.398 ms第 34 层后仍占 7.29%
B256 target 尾部3.180 ms / 总 37.489 ms第 34 层后仍占 8.48%
draft batch 16.052 ms一份完整 proposal 的微基准
draft batch 46.287 ms6.287/6.052=1.039，多三个假设只增 3.9%

Probe B 只证明硬件必要条件：存在 2.7–3.2 ms 窗口，小批量 drafter 很平坦。它没有运行第二张 GPU，也没有证明 6.05 ms 草稿能被 3 ms 尾部完全隐藏。

6.4 Probe C：把 feature 就绪点从第 34 层提前到第 26 层

SelectedHiddenCollector.selected_states() 实现三种模式；提示预填和每轮接受路径的 feature 收集共用同一逻辑。

exact       = [h1, h9, h17, h25, h33]
repeat25    = [h1, h9, h17, h25, h25]
extrapolate = [h1, h9, h17, h25, 2h25-h17]
模式接受保留率轮次TPOT 相对 exact
exact100%1,1731.000×
repeat2585.90%1,3881.164×，即 +16.36%
extrapolate86.70%1,3731.142×，即 +14.22%

86.70% 是三个数据集各自“近似模式每轮接受数 ÷ exact 每轮接受数”的宏平均；不是准确率。+14.22% 是实际生成 TPOT 比 exact 高 14.22%，也就是更慢。外推模式 acceptance 下降使 target 轮次从 1,173 增至 1,373（+17.0%），多出的完整 target forward 抵消了更早启动 drafter 的潜在收益。

7. 算法 4：错误前缀 target state 的朴素回收

7.1 具体例子

真实前缀 P，草稿走了错误词元 x
target 已经并行算出：
  p(. | P,x), p(. | P,x,y), ...

target 最终给出的正确 bonus 是 b

朴素回收：
  从错误状态分布中取候选 a,c,...
  把它们平移到正确前缀 P,b 后
  在正确 target KV cache 上重新验证

注意：p(. | P,x) ≠ p(. | P,b)
旧状态只作为 proposal，绝不直接提交

7.2 实现了四种构树器

build_rejected_state_recycling_tree() 支持局部后代、全树同深度 target argmax 和原 draft suffix；最强版本 build_depth_mixture_recycling_tree() 在每个未来深度收集所有错误状态的完整词表分布，对每个 token 取跨状态最大归一化分数，再调用 DDTree 构造 B64 前缀闭合树。

错误状态 logits（同一未来深度）
    │ log_softmax
    ▼
对每个 token 取所有错误状态中的 max score
    │ 再归一化并保留 top-64
    ▼
DDTree best-first search → B64 回收树
    │
    ▼
正确 cache P,b 上 shadow verify
    │
    ▼
与同一 P,b 的正常下一轮 DARTree 配对

7.3 17.28% 和 -57.14% 的分母

283 个可配对轮次中，最强混合树在 237 轮非空，因此可用比例 237/283=83.75%。只看这 237 轮：

路径平均总接受其中 bonus 之外
正常下一轮完整 DARTree8.422—
错误状态混合回收1.4560.456

因此接受保留率是 1.456/8.422=17.28%。1.456 中的 1 是已经由 target 产生的 bonus，旧状态真正额外贡献只有 0.456 token。策略在有树时用回收、无树时回退正常 DARTree；按实测 build + 38.39 ms verify 做逐轮成本投影，accepted-token/ms 相对全正常 DARTree 为 -57.14%。它不是完整回收轨迹的 E2E TPOT，但接收长度相差近六倍，调度优化无法逆转。

8. 算法 5：用 bonus token 重置 Domino GRU

8.1 与错误 target state 回收有什么不同

这里不再复用因果前缀错误的 target hidden state，而是复用 DFlash 一次并行算出的块位置 z_i。Domino 本来就用 GRU 为每条树分支注入具体前缀，因此可以丢弃错误分支 GRU state，用真实 bonus 重置。

例：b16 当前轮在深度 d=5 停止
已接受：P → A → B → C → D → E
target bonus：F

replay_domino_prefix_hidden(P,A,B,C,D,E)
        │
        ▼
stop_hidden
        │ 输入真实 F
        ▼
reset_hidden = GRU(F, stop_hidden)
        │
        ▼
切片复用 z[d+1 : 16]，只剩 16-d-1 个位置
        │
        ├─ build bonus_reset_chain
        └─ build bonus_reset_dartree (B64/W12)
        │
        ▼
在正确前缀 P,A,B,C,D,E,F 上重新验证

8.2 实际代码

  • replay_domino_prefix_hidden() 从零状态依次重放根和已接受 token，再输入 bonus。
  • build_bonus_reset_tree() 设置 slot_offset=stop_depth+1，同步切片 parallel_hiddens/base_logits/z_parts/candidate_tables。
  • build_dartree_supertree() 新增 initial_root_hidden，让重置状态成为新树根状态。
  • build_fresh_horizon_tree() 在正确 bonus 前缀上重新跑 DFlash，但裁成相同剩余长度，作为质量上限。

8.3 三个百分比使用三个不同分母

283 个配对轮次中，228 轮还有至少一个未消费位置，因此可用比例 228/283=80.57%，平均只剩 9.05 个位置。

方案平均总接受bonus 外接受平均 proposal+verify
正常下一轮完整 DARTree8.215—51.285 ms
reset DARTree2.6321.63244.727 ms
正确前缀同长度重算3.2632.26350.485 ms
  • 72.09%：1.632 / 2.263。分母是“正确前缀上重新跑 DFlash、但裁成同样 9.05 个位置”的 bonus 外接受数，只衡量旧 z_i + GRU reset 的质量。
  • 32.03%：2.632 / 8.215。分母是正常下一轮完整 b16 DARTree 的总接受数，衡量它能否直接替代下一轮。
  • -42.76%：有剩余位置时用 reset DARTree，否则正常回退的逐轮 accepted-token/ms 变化。虽然每轮省 6.56 ms，但接受长度少 68%，仍要支付约 38 ms target verify。

决定性对照是“同长度重算”本身也只有正常下一轮的 39.72%，单位时间仍为 -42.42%。即使训练把 72.09% 提到 100%，当前块剩余 horizon 太短，仍无法直接替代下一轮，因此没有启动 50.8M 参数修正器训练。

9. 算法 6：严格连续匹配后缀回收

9.1 算法只保留原树中真实存在的连续边

真实前缀 P，target bonus=b
原错误分支：P → x → a → c → d

target 在 P,x 后预测 a
  原树确有 x→a：保留 a
target 在 P,x,a 后预测 c
  原树确有 a→c：保留 c
target 在 P,x,a,c 后预测 e
  原树下一边是 d，不匹配：立即停止

得到回收候选：P → b → a → c
然后在正确 P,b cache 上重新验证 a,c

build_verified_suffix_recycling_tree() 对停止节点的每个被拒绝子节点循环执行：读取该错误节点的 target argmax，用 child_map[(parent, token)] 查询原树是否存在完全相同的边；存在才加入前缀树并继续，否则立即停止。多条链只合并公共前缀，不合成新边。

11. 下一步方向

11.1 第一优先级：真实 ragged batch 动态预算

在线请求集合 {(prefix length Li, uncertainty ui)}
        │
        ▼
根据当前 batch 与 Li 估计共享 query capacity Q
        │
        ▼
先给每请求最小 B，再按 ui 分配剩余节点
        │
        ▼
一次 target forward 验证多棵不同大小的树
        │
        ▼
比较固定 B64 / 固定 B256 / 固定总 query / 动态分配
指标：吞吐、TPOT、P95 latency、acceptance、公平性

这是 27.16% roofline 结果真正缺少的端到端实现。控制器必须同时考虑前缀长度、batch size、构树时间和预算带来的 acceptance 边际收益，不能只选平台区最大的 B。

11.2 若允许训练：原生多 horizon drafter

联合训练 block 8/16/24/32 或不同 mask ratio，让一次 forward 直接覆盖更远位置，避免 stale second block 的第二次 draft 和旧 feature。它也能解决 bonus reset 的核心限制：当前块停止后平均只剩 9.05 个位置。

11.3 较低优先级：第 34 层完整状态蒸馏

训练小预测器联合预测停止路径和 bonus token，先把 top-8 完整命中从 48.17% 提升到至少 90%，再实现真实双卡 P2P overlap。若只提高路径命中、不预测 bonus，下一轮 cache 仍不可复用。

11.4 不再优先投入

不继续枚举固定 feature 外推系数，不扩大错误 target state 混合树，不为严格后缀单独训练选择器，也不优化其 0.168 ms 构树时间；这些方向的主要损失来自候选质量和目标验证轮数，而不是 Python 开销。
