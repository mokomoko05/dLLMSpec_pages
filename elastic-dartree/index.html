摘要

本组实验追问：除“用树提高 acceptance、用满空闲 verification budget”之外，训练无关的 diffusion drafter 还能否通过动态容量、跨轮多块、跨卡预取或拒绝后状态回收获得新收益。

最可信的正结果是硬件容量规律：短上下文下 A100 的总低延迟 query 容量约为 256，batch 1/2/4 对应每请求 B256/B128/B64；长上下文下降到约 128 或 64。仅看 target verification，动态选择预算相对固定 B256 平均降时 27.16%，但尚未证明真实多请求端到端收益。其余无训练捷径均未过门槛，表明主要瓶颈不是树形搜索，而是 drafter 的预测范围和对最新 target feature 的依赖。

1. 问题与实验边界

硬件1 × A100 80GB PCIe
精度 / backendBF16 / Transformers SDPA
主数据集GSM8K、HumanEval、Alpaca

不在范围内真实双卡 P2P、真实多请求 ragged DARTree、训练新 drafter/refiner

DARTree 已把分支条件化与横向验证容量结合，但仍有两个硬边界：一次只产生训练块长内的 16 个位置；下一轮 drafter 必须等待本轮 target 中间表示。所有探针都围绕这两个边界展开，并保持候选最终由 target 验证。

2. 动态 target verification capacity

单请求 B256 的收益说明 target query 数存在平台区，但服务负载和 KV 长度会改变平台边界。容量 roofline 显示，短上下文时总低延迟容量近似守恒：

表 1. 短上下文容量规律
并发 batch每请求建议预算总 query 量级
1B256约 256
2B128约 256
4B64约 256

长上下文会将总容量降至约 128 或 64。只计算 target verification phase，容量感知选择相对固定 B256 平均减少 27.16% 时间；这不是端到端结果，因为真实 ragged batch 还要加入构树、调度、padding、每请求 acceptance 与队列动态。

B384 单请求的端到端反例进一步说明，静态扩大预算不是主线：更大的树可能增加 acceptance，却跨过硬件平台并失去 TPOT 收益。真正值得实现的是按 batch、前缀长度和实时负载分配共享容量。

3. 超出 b16 的跨轮多块预测

验证平台还能容纳更多节点，看似可以用过期 target feature 立即构造第二块，将预测范围从 16 扩到 32。正式 stale-feature probe 的结果是：第二块每轮仅多接受 0.013 token，单位时间接受词元下降 9.61%。

这并不意味着更长预测深度没有价值。事后提供真实接受分支和精确 target feature 时，满深度轮次还能多接受约 7.94 token；失败点是当前 drafter 强依赖最新目标表示，旧 feature 无法支撑正确的下一块。后续若追求更深预测，需要原生多长度训练、feature predictor 或能在一次 forward 内覆盖更远 horizon 的架构。

4. 特征就绪后的跨卡预取

Qwen3-4B 共 36 层，Domino 最后一路 target feature 在第 34 层后已经产生；此时还剩最后两层、norm 和词表头。第二张 GPU 若能提前猜中完整下一状态，就可能在这段尾部窗口预计算下一轮 drafter。三个探针分别检查算法状态、硬件窗口和早层特征质量。

5. 拒绝后的状态回收

target 拒绝候选时会产生真实 bonus token。实验检查了三类“不要立刻重跑完整下一轮”的方案：

表 3. 状态回收探针
方案核心结果单位时间结果
错误 target state 混合回收接受保留率 17.28%-57.14%
bonus-token GRU reset相对同长度重算保留 72.09%；相对完整下一轮保留 32.03%-42.76%
严格连续匹配后缀可迁移边比例 15.53%无条件使用 -19.15%

错误 target hidden state 已深度绑定错误词元，不能通过简单混合恢复正确前缀。GRU reset 在数学和质量上明显更合理：丢弃错误分支状态，将真实 bonus token 输入 Domino GRU，再复用尚未消费的并行位置；但停止深度越大，b16 中剩余位置越少。即使同长度质量接近门槛，截断后的预测长度也不足以摊薄一次完整 target verification。

严格连续匹配后缀证明部分旧边确实会在正确前缀下再次出现，但迁移稀疏且高度条件化。若没有低成本、校准良好的触发器，无条件回收仍为负收益。

这些负结果共同定位了瓶颈：verification budget 仍有系统空间，但当前 b16 drafter 没有饱和的是“横向 target 容量”，而不是可无代价回收的“纵向未来状态”。

7. 下一步可能方向

7.1 首选：真实异构多请求的共享预算控制器

实现 ragged DARTree batch，让控制器根据每个请求的 KV 长度、当前 batch size、proposal uncertainty 和在线 roofline 分配 B64/B128/B256。需要报告真实服务吞吐、TPOT、尾延迟、acceptance 与公平性，并与固定 B64/B256 比较；这是当前证据最强、训练无关且有明确端到端缺口的方向。

7.2 构树宽度与验证预算双控制

硬件决定总 verification budget，输入不确定性决定 construction width。可使用 drafter entropy、top-k gap、分支质量集中度或历史 acceptance 作为无训练信号，在固定总预算内把节点分配给更不确定的请求。

7.3 原生多预测长度 drafter

若允许轻量训练，联合训练 block 8/16/24/32 或不同 mask ratio，使预测 horizon 随硬件容量和停止深度变化。它直接解决 stale second block 与 bonus reset 的共同限制：现有 b16 之外没有可靠位置。

7.4 目标尾部状态蒸馏

训练小预测器，从第 34 层 feature 联合预测停止节点与 bonus token，把 top-8 完整状态命中率从 48.17% 提到至少 90%，再在真实双卡上利用 2.73–3.18 ms 尾部窗口。评测必须包含未参与训练的数据集和猜错浪费。

7.5 选择性而非无条件的回收

仅在短接受路径、低熵、连续后缀高置信时触发 GRU reset 或 suffix recycling；规则应在留一数据集上选择，在未参与规则选择的数据集仍实现正收益。当前迁移率低，这条优先级显著低于动态共享预算。

8. 代码、验证与限制

运行时基于 VILA-Lab/DARTree@5bb3240，历史快照固定为 exp/dartree-elastic-probes@642a41a。目录保留 14 份中文报告、runner、分析脚本、结构测试、容量小网格与聚合 JSON；约 95 MiB 的逐轮 raw JSON、日志和缓存未进入 Git。

所有 Python 文件通过 py_compile；upstream 相关 11 个 unittest、本目录 2 个 capacity unittest 与 17 个函数测试通过。各旁路 probe 不提交 token，正式主路径输出与对照保持一致。

动态容量的 27.16% 是 target verification phase reduction，不是端到端加速；Probe B 的复制测量也不是实际双卡 P2P。实验早于当前 clean-gate 规范，归档没有补造正式运行前 provenance。
