摘要

本实验沿 DARTree 的系统瓶颈展开：先测量 target verification 容量随前缀长度和 batch size 的变化，再尝试把剩余容量用于更深预测、跨卡预取和拒绝后状态回收。所有候选仍由完整 target 模型验证，因此这些改动只影响 proposal 和运行时间，不改变生成分布。

动态验证预算是唯一保留的主线。在 18 个“前缀长度 × batch size”状态上，按 5% 延迟平台选择预算，使 target verification 阶段相对固定 B256 平均减少 27.16% 延迟；端到端收益仍需在真实 ragged batch 中验证。其他方案均未达到继续门槛：stale second block 缺少新的 target feature；跨卡预取的完整状态命中率不足；早层特征替代降低 acceptance；三种状态回收方案无法在正确新前缀下保留足够候选质量。

1. DARTree 基线流程

DFlash/DOMINO drafter 不是独立的小语言模型。它读取目标模型已经确认的上下文，并抽取目标模型从 0 开始编号的 [1,9,17,25,33] 层隐藏表示，也就是第 2/10/18/26/34 个 Transformer block 的输出；随后一次并行生成 16 个位置的基础分布。Domino 的 GRU 根据每条具体前缀修正这些并行分布，DARTree 再把多条分支组织成一棵树。

1.1 从 Target feature 到 DFlash 并行表示

下面的维度来自本实验实际使用的 Qwen3-4B / Domino-b16 checkpoint。令请求 batch size 为 N、已确认前缀长度为 L、并行草稿块长为 S=16。

符号实际维度数据
H2,560Target、DFlash 和 token embedding 的 hidden size
G1,024Domino prefix GRU 的路径状态维度
M256Domino logit 修正 MLP 的中间维度
V151,936Qwen3 词表大小

Target 在上述五个 block 分别产生一个 [N,L,2560] hidden tensor。代码先沿最后一维拼接五路 feature，得到 C∈RN×L×12800，再用一个无 bias 线性层压回 2,560 维并做 RMSNorm：

C = concat(H(1), H(9), H(17), H(25), H(33)) C′ = RMSNorm(C WcT),   Wc ∈ R2560×12800

当前词元与后面的 mask token 先查 Target 的 embedding table，形成 X0∈RN×16×2560。DFlash 有 5 个 decoder layer；每层只用块表示产生 query，而 key/value 同时来自压缩后的 Target 上下文和当前块表示：

Q = RMSNorm(XWq),   K = RMSNorm([C′;X]Wk),   V = [C′;X]Wv Attention(X,C′) = softmax(QKT/√d) V X ← X + WoAttention;   X ← X + MLP(RMSNorm(X)) 矩阵乘法负责通道混合和注意力聚合；RMSNorm、softmax、残差加法是逐元素或按行运算。

首次 prefill 时，C′ 覆盖整段 prompt；之后每轮只把新接受路径的五路 feature 送入 DFlash，先前位置保存在 draft KV cache 中。DFlash 临时计算整个 16-token 块，构造 proposal 后再把 draft cache crop 到真实已确认长度，未被 target 接受的位置不会进入下一轮缓存。

5 层结束并再次 RMSNorm 后得到 Z∈RN×16×2560。Target 自己的 lm_head 将每个并行位置投影到完整词表，形成基础 logits：

Lbase = Z WlmT ∈ RN×16×151936

这 16 个位置是一次并行算出的，因此 Lbase[i] 本身不知道树上某条具体路径已经选择了哪些 token。Domino GRU 的作用就是把这部分因果前缀补回来。

1.2 Domino GRU 的矩阵和逐元素运算

对树上任意一条路径，令当前 token embedding 为 xt∈R2560，父路径状态为 ht-1∈R1024。checkpoint 使用单层、无 bias GRU。两次矩阵乘法分别产生输入项和循环项：

矩阵乘gi = Wihxt,   Wih∈R3072×2560 矩阵乘gh = Whhht-1,   Whh∈R3072×1024 gi=[ir,iz,in],   gh=[hr,hz,hn] 逐元素rt=σ(ir+hr),   zt=σ(iz+hz) 逐元素nt=tanh(in+rt⊙hn) 逐元素ht=(1-zt)⊙nt+zt⊙ht-1

rt 是 reset gate，控制旧状态参与候选状态计算的比例；zt 是 update gate，在新候选状态 nt 与旧路径状态之间逐维插值。所有 sigmoid、tanh、乘法 ⊙ 和加法都在 1,024 个 hidden channel 上逐元素执行。

实现还预先计算整张词表的输入投影表 T=EvocabWihT∈R151936×3072。扩展 token v 时直接 gather T[v]，只需再计算父状态的 Whhh；这样避免每个树节点重复执行 embedding lookup 后的 2,560→3,072 GEMV。

1.3 路径状态如何修正候选 logits

Domino 的修正网络接收同一位置的 DFlash 表示 zi∈R2560 和当前路径 GRU 状态 hp∈R1024。第一层权重按输入切成 Wz∈R256×2560 与 Ws∈R256×1024：

矩阵乘ui,p = Wzzi + Wshp ∈ R256 逐元素mi,p = SiLU(ui,p) = ui,p⊙σ(ui,p) 矩阵乘Δℓi,p = W2mi,p,   W2∈R151936×256 ℓi,p = Lbase[i] + Δℓi,p

因此，同一个并行位置 i 的 zi 和基础 logits 可以被所有父节点共享；不同父节点只因 hp 不同而得到不同修正分布。当前 checkpoint 的 pure_draft_prefix_len=1，第一层候选直接使用基础 logits；从下一层开始才使用路径 GRU 修正。

DARTree 不为每个父节点计算完整的 151,936 维修正。代码先从该位置的基础 logits 取 K64 候选，并 gather W2 对应的 64 行，随后执行 [父节点数,256] × [256,64] 的矩阵乘法，只为这 64 个词元计算路径修正。

1.4 DARTree 扩展、剪枝和 Target 验证

构树从当前根词元开始。每个深度上，所有 frontier 父节点共享位置 i 的 DFlash 表示，但各自携带独立 GRU 状态。对每个“父节点 × K64 候选”计算累计路径分数：

score(child) = score(parent) + logsoftmaxK64 candidates(ℓi,parent)[token]

W48 构造在每个深度全局保留分数最高的最多 48 个父子组合，再分别用所选 token 更新 GRU 状态。16 个深度最多形成约 48×16=768 个 supertree 节点。最后按 path score + depth_bonus×depth 全局选出 B 个节点；本实验 depth_bonus=-0.2，父节点分数总是不低于后代，因此 Top-B 结果保持前缀闭合。

保存的数据用途
token[node]该树节点代表的候选词元
parent[node]恢复路径、更新 branch-local GRU、构造 child map
depth[node]设置绝对 position id：current_position + depth
visibility[node,ancestor]让节点只看已确认 prefix、自己的祖先和自己，不能看到兄弟分支

送入 Target 的 query 是“当前根 + B 个树节点”，所以 B256 对应 257 queries。一次完整 Target forward 同时给每个节点产生下一 token logits。验证从根开始：若当前节点的 target argmax 恰好是某个子节点 token，就沿该边继续；第一次没有匹配子节点时停止，该 argmax 成为 bonus token。

Target forward 暂时为整棵树产生 KV 和五路 hidden feature；提交时只按接受节点索引 gather 连续路径，compact KV cache，并丢弃所有未接受分支。下一轮 DFlash 读取的仍然是完整 Target 在真实已接受路径上产生的 feature，因此 DARTree 改变的是并行 proposal 形状，不改变最终 target 分布。

1.5 一个具体词元例子

本轮提交：A、B、D，其中 A/B 是被接受的 draft，D 是 target bonus token。

下一轮真实前缀：P + A + B + D。

实验中的“单轮接受长度”或 τ 指一次 target verification 让输出前进的 token 数，即“连续匹配的 draft token + 最后的 target bonus token”。b16 的上限是 17。所有新方案产生的 token 都只作为候选，并在正确 target KV cache 上重新验证。

4. 动态验证预算

4.1 容量测量实现

run_capacity_roofline.py 为每个 batch element 建独立 DynamicCache，构造前缀闭合的树 visibility mask，并真实执行完整词表输出和 argmax。对每个前缀长度 L、batch size N 和预算 B 测 target latency。

4.2 具体例子：前缀 512、batch 4

固定 B256 时，一批要验证 4×257=1028 个 query；容量选择器改为每请求 B64，总 query 为 4×65=260。B64 的验证延迟为 37.909 ms，相对该状态的固定 B256 低 52.46%。减少的是一次 target verification 的 latency，不包含 acceptance 下降后可能增加的轮次。

4.3 验证延迟收益

对 6 个前缀长度 × 3 个 batch size 的 18 个状态，分别计算

saving(L,N) =
  [Tverify(B256) - Tverify(Bselected)] / Tverify(B256)

18 个状态的 saving 算术平均为 27.16%，中位数 20.19%，最大 63.70%；14/18 个状态选择的预算小于 B256，3 个等于 B256，1 个选择 B384。因此，容量选择在 target verification 阶段平均减少 27.16% 延迟；该结果不包含预算变化对 acceptance 和解码轮次的影响。

B384 相对 B256 将接受长度提高 2.81%，但三数据集 TPOT 宏平均增加 0.93%。因此 B384 的端到端结果更慢，预算选择还需要考虑 acceptance 的边际收益，不能只依据硬件延迟平台。

6. 第 34 层就绪后的跨卡预取

6.1 设想的双卡流程

这个方案需要三个条件同时成立：A 能用少量假设覆盖真实状态；B target 尾部有足够时间且 drafter 小批量高效；C 或者能更早得到可用 feature，扩大重叠窗口。

8. Bonus token 重置 Domino GRU

8.1 方法区别

这里不再复用因果前缀错误的 target hidden state，而是复用 DFlash 一次并行算出的块位置 z_i。Domino 本来就用 GRU 为每条树分支注入具体前缀，因此可以丢弃错误分支 GRU state，用真实 bonus 重置。

8.2 实际代码

  • replay_domino_prefix_hidden() 从零状态依次重放根和已接受 token，再输入 bonus。
  • build_bonus_reset_tree() 设置 slot_offset=stop_depth+1，同步切片 parallel_hiddens/base_logits/z_parts/candidate_tables。
  • build_dartree_supertree() 新增 initial_root_hidden，让重置状态成为新树根状态。
  • build_fresh_horizon_tree() 在正确 bonus 前缀上重新跑 DFlash，但裁成相同剩余长度，作为质量上限。

9. 严格连续匹配后缀回收

9.1 算法只保留原树中真实存在的连续边

真实前缀：P，target bonus = b。

原错误分支：P → x → a → c → d。

  1. 保留第 1 边target 在 P,x 后预测 a；原树存在 x → a，因此保留 a。
  2. 保留第 2 边target 在 P,x,a 后预测 c；原树存在 a → c，因此继续保留 c。
  3. 停止target 在 P,x,a,c 后预测 e；原树下一边是 d，第一次不匹配后立即停止。

回收候选：P → b → a → c；随后在正确的 P,b cache 上重新验证 a、c。

build_verified_suffix_recycling_tree() 对停止节点的每个被拒绝子节点循环执行：读取该错误节点的 target argmax，用 child_map[(parent, token)] 查询原树是否存在完全相同的边；存在才加入前缀树并继续，否则立即停止。多条链只合并公共前缀，不合成新边。

11. 下一步方向

11.1 第一优先级：真实 ragged batch 动态预算

Roofline 已证明容量随前缀长度和 batch size 变化；下一步需要把该规律接入真实 ragged batch。控制器必须同时考虑构树时间和预算带来的 acceptance 边际收益，而不是只选择平台区最大的 B。

11.2 若允许训练：原生多 horizon drafter

联合训练 block 8/16/24/32 或不同 mask ratio，让一次 forward 直接覆盖更远位置，避免 stale second block 的第二次 draft 和旧 feature。它也能解决 bonus reset 的核心限制：当前块停止后平均只剩 9.05 个位置。

11.3 较低优先级：第 34 层完整状态蒸馏

训练小预测器联合预测停止路径和 bonus token，先把 top-8 完整命中从 48.17% 提升到至少 90%，再实现真实双卡 P2P overlap。若只提高路径命中、不预测 bonus，下一轮 cache 仍不可复用。

11.4 不再优先投入

不继续枚举固定 feature 外推系数，不扩大错误 target state 混合树，不为严格后缀单独训练选择器，也不优化其 0.168 ms 构树时间；这些方向的主要损失来自候选质量和目标验证轮数，而不是 Python 开销。
