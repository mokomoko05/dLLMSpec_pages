vLLM 兼容回移、七数据集服务评测，以及官方 selector 驱动的 ours tree 验证

摘要

本实验比较 Qwen3.8-27B 原生自回归、Inco AI DFlash2 和 RadixArk DSpark 的服务性能。本机实验使用固定的 vLLM 0.26.0、PyTorch 2.11.0+cu129 兼容回移，结论对应 A100/vLLM 环境。

在七个数据集上，DFlash2 与 DSpark 都稳定加速原生生成；DFlash2 在并发 1 和 8 的所有数据集上都快于 DSpark。并发 1 的总吞吐加速为 2.76× / 2.29×，并发 8 为 2.20× / 1.86×，差异与 DFlash2 更高的 speculative acceptance 一致。

ours tree 直接加载官方 Qwen3.8-27B target 与 DFlash2 checkpoint，使用官方 selector edge scores 构造 21-node、最多二分枝的候选树。在 MATH-500、HumanEval、MBPP、LiveCodeBench、MT-Bench first turn 与 AIME25 共 190 条请求上，pooled per-request mean tau 从官方 base 的 5.9269 提升到 6.6025（+11.40%，paired bootstrap 95% CI [10.24%, 12.57%]），verification steps 减少 14.45%；190/190 输出一致，166/23/1 条请求提高/持平/下降。当前 tree backend 采用多次 target leaf replay，作为正确性 reference；一次 flattened tree forward 版本完成后再评测延迟。

实验只测服务性能，不执行模型生成的代码、不判题，也不评估回答质量。两种 drafter 都提出 7 个候选词元，并与同一 target、请求顺序和采样配置比较。

2. 兼容实现

SGLang PR 35371 的构建链需要 CUDA 13，而本机驱动只支持当前 CUDA 12.x 栈。实验因此回移 vLLM PR 52816 的 DFlash2 支持，并固定为可在驱动 550.54.15 上运行的 CUDA 12.9 wheel 组合。

兼容 patch 补齐模型注册、layer override、稀疏 draft logits、Gumbel selection 与 torch.topk fallback；DSpark 通过 config-only adapter 映射到 vLLM 的 Qwen3DSparkModel，权重保持原 checkpoint。FlashInfer JIT 所需的本机 libcuda.so、LIBRARY_PATH 与 Conda C++ runtime 均由启动脚本固化。

3. 评测方法

  1. 分别启动 vanilla、DFlash2 和 DSpark 服务；每个数据集、每种方法先发送不计时 warmup。
  2. 并发 8 矩阵对每种方法发送 414 个请求，最多生成 512 tokens。
  3. 并发 1 矩阵对每种方法发送 750 个请求，最多生成 2048 tokens。
  4. 逐请求记录 latency、TTFT、TPOT、completion tokens 与 speculative counter，再按方法和数据集聚合。

冷启动请求会触发 speculative 路径的 Triton JIT。未经 warmup 的第一次请求不能与原生路径直接比较，正式矩阵均排除了该成本。

6. 官方 Selector 驱动的 ours tree

6.1 对照方法与 tree builder

实验固定官方 target checkpoint Qwen3.8-27B 和官方 draft/selector checkpoint Qwen3.8-27B-DFlash2。base 行运行 vLLM official DFlash2：candidate selector 计算 edge scores，官方 selector walk 逐 slot 取 edge-score argmax，得到 7-token trunk并执行标准线性 speculative verification。ours 使用同一份 edge scores，完整保护 official trunk，再按累计 path probability 在 max_nodes=21、max_branching=2 预算内扩展 prefix-closed 分枝。

target runner 为每个 leaf 恢复同一 KV/GDN 快照，执行线性 target replay，选择 target greedy prediction 匹配最长的 leaf；随后再次恢复快照并重放选中路径，使 cache、hidden state 与 scheduler commit 保持一致。公共前缀 prediction 跨 leaf 必须一致，否则 fail closed。

6.2 多数据集正式结果

评测覆盖 MATH-500、HumanEval、MBPP、LiveCodeBench、MT-Bench first turn 各 32 条及 AIME25 30 条。每请求最多生成 2048 tokens，temperature=0、thinking off、concurrency 1；每数据集先执行 1 条 128-token warmup。每请求计算 tau_i = 1 + accepted_i / verification_steps_i，再对请求等权平均。

6.3 在线与离线评测流程

在线流程依次完成服务启动、128-token warmup、顺序请求、target verification、cache update 和 scheduler commit。scheduler 在输出提交点按 request ID 记录 accepted draft tokens 与 verification steps；ours runner同时记录 leaves、selected path、accepted count 和 replay 次数。official 在 GPU1 顺序完成六个数据集；ours 在两张相同 A100 上分配互斥数据集，每个请求仍使用单卡、单服务和 concurrency 1。

离线流程按 request ID 对齐请求 JSON、scheduler committed trace 与 tree replay trace，比较 official/ours 输出，逐请求计算 tau，并汇总 mean、median、sample stdev、p05、p95、回退数和 paired bootstrap CI。异步 stale frame 在 committed step 对齐时排除。双卡分片只缩短运行墙钟，tau 口径不变；reference backend 的多次 target replay使 latency 和吞吐不进入本表。

6.4 局部回退与验收状态

LiveCodeBench sample 14 是唯一请求级回退：输出 79 tokens，official 为 11 steps、69 accepted、tau 7.2727；ours 为 12 steps、68 accepted、tau 6.6667。相同 prompt 与 seed 的隔离复验稳定复现，输出保持一致。ours 在一次 off-trunk 路径接受 7 tokens 后连续两轮接受 0，说明新的 verification block boundary 改变了下一轮 target hidden states 与 GDN speculative state 轨迹。tree 在固定 step 包含 official trunk，同时整请求轨迹仍可能产生局部回退。

全矩阵状态为 COMPLETED_WITH_REGRESSION：五个数据集通过逐请求 non-regression gate，LiveCodeBench 保留 1 个有效回退点并标记 INVALID，全量结果不写 SUCCESS。当前证据支持“多数据集平均 tau 显著提高”，同时保留“190 条中 1 条下降”的适用边界。

7. 结论与限制

  1. Qwen3.8-27B 的 DFlash2 和 DSpark 可在单张 A100 80GB 上通过固定 vLLM/CUDA 12.9 组合运行。
  2. 两种方法在并发 1/8 都加速原生服务，DFlash2 因 acceptance 更高而稳定领先 DSpark。
  3. 官方 selector 驱动的 ours tree 已跑通完整 vLLM draft、target verify、cache update 与 scheduler commit 链路；六数据集 190 请求 pooled mean tau 提升 11.40%，95% CI [10.24%, 12.57%]，输出保持一致。
  4. 逐请求结果为 166 条提高、23 条持平、1 条下降。该局部回退来自 block boundary 改变后的跨轮状态轨迹，完整报告保留此反例。
  5. tree 当前是多次 leaf replay 的正确性 reference；一次 target forward 的性能后端完成后再报告 latency 与吞吐。

8. 最新 tree 实现索引

最新实现位于 vLLM fork exp/dflash2-singlepath-sanity@24ea78c。tree_builder.py 先校验官方 checkpoint 的 selector/convolution tensor，再接收 candidate_ids[B,slots,top_k]、edge_scores[B,slots,top_k,top_k] 和 anchor。builder 对 successor 维度执行 log_softmax(edge_scores / temperature)，从 predecessor rank 0 逐 slot argmax 得到 7-token protected trunk。

剩余节点以累计路径概率的 best-first heap 顺序扩展。每个候选保存 parent、depth、candidate rank、token 和累计 log probability；候选的所有祖先必须已经存在，单一 prefix 最多两个 child，重复 token、无效 successor、低于 min_path_probability 或达到 21 节点预算时停止。最终生成扁平 token 数组、parent indices、position ids、ancestor mask 和 root-to-leaf paths。

serving 侧由 DFlash proposer 在 VLLM_DFLASH2_TREE=1 时生成 metadata；target runner 根据 ancestor mask 处理 flattened tree，或在 correctness reference 模式下保存 KV/GDN snapshot、逐 leaf replay、检查公共前缀 prediction 一致性、选择最长 target-matching leaf，恢复并重放最终路径后提交 bonus token。scheduler 仍以 protected trunk 做接口校验。

代码阅读入口：tree_builder.py:25 checkpoint 校验，:286 builder，:292 score 归一化，:312 单请求扩展，:434 official model 接口，:471 vLLM serving 接口；dflash.py:84 proposer 接入；tree_metadata.py:6 metadata，:33 ancestor mask，:45 verification；model_runner.py:1568 replay gate，:1600 leaf replay；tree_replay.py:108 trunk 对齐，:147 replay decision。完整中文伪代码与反例解释见 dLLMSpec 实验报告的 TREE_METHOD.md。

9. 单次 flattened target forward 正式结果

最新 ours backend 已把 anchor + 21 tree nodes 放入一次 target model forward。每轮仍使用官方 Qwen3.8-27B-DFlash2 checkpoint：compute_candidates 生成候选，官方 candidate_selector 输出 predecessor→successor edge scores；builder 完整保护官方 7-token argmax trunk，再按累计 path probability 以 best-first 顺序扩展 prefix-closed 分枝，预算为 max_nodes=21、max_branching=2。

full-attention 节点只能读取历史 KV 和自己的 ancestor chain；GDN leaf 从相同 conv/SSM snapshot 出发，并为每个节点保存完整 rolling buffer 与 recurrent state。target greedy verification 在所有 root-to-leaf path 中选择最长匹配路径，随后只提交命中路径 KV/GDN state。selector score 只用于分配候选预算，最终接受完全由 target logits 决定。线性退化 sanity（7 nodes、单分枝）在 GSM8K 前 6 条上实现输出与 per-request tau 逐项等于 vLLM official DFlash2。

9.1 在线与离线流程

在线流程固定单卡单服务、concurrency 1：启动服务→每数据集 128-token warmup→按固定顺序发送 greedy、thinking-off 请求→scheduler 按 request ID 记录 committed accepted tokens 与 verification steps→ours 额外记录 tree layout、命中路径与 target forward 次数。两卡只承载互斥数据集分片，不把同一请求跨卡或批处理。

离线流程按 request ID 对齐响应、scheduler trace 和 tree trace；逐请求计算 tau_i=1+accepted_i/steps_i 与 throughput_i=completion_tokens_i/latency_i，再汇总 mean、median、stdev、p05、p95。汇总器同时检查请求完整性、boxed 答案、trace 唯一归属和每 step 单 forward，失败点不会进入正式 SUCCESS。

代码与完整中文数据流见 正式实验目录、TREE_METHOD.md 与 per-request JSON。
