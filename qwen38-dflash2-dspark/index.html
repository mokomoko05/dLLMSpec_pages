摘要

本实验比较 Qwen3.8-27B 原生自回归、Inco AI DFlash2 和 RadixArk DSpark 的服务性能。官方 SGLang 路径依赖 CUDA 13；本机实验使用固定的 vLLM 0.26.0、PyTorch 2.11.0+cu129 兼容回移，因此结论对应 A100/vLLM 环境。

在七个数据集上，DFlash2 与 DSpark 都稳定加速原生生成；DFlash2 在并发 1 和 8 的所有数据集上都快于 DSpark。并发 1 的总吞吐加速为 2.76× / 2.29×，并发 8 为 2.20× / 1.86×，差异与 DFlash2 更高的 speculative acceptance 一致。

2026-09-14 的新增实验直接加载官方 Qwen3.8-27B target 与 DFlash2 checkpoint，使用官方 selector edge scores 构造 21-node、最多二分枝的 ours tree。GSM8K 前 32 条、greedy、关闭 thinking、并发 1 的正式在线评测中，per-request 平均 tau 从官方 base 的 6.3188 提升到 7.1303（+12.84%）；32/32 输出一致，32/32 请求 tau 提升。当前 tree backend 采用多次 target leaf replay，定位为正确性 reference，延迟留待一次 flattened tree forward 版本评测。

实验只测服务性能，不执行模型生成的代码、不判题，也不评估回答质量。两种 drafter 都提出 7 个候选词元，并与同一 target、请求顺序和采样配置比较。

2. 兼容实现

SGLang PR 35371 的构建链需要 CUDA 13，而本机驱动只支持当前 CUDA 12.x 栈。实验因此回移 vLLM PR 52816 的 DFlash2 支持，并固定为可在驱动 550.54.15 上运行的 CUDA 12.9 wheel 组合。

兼容 patch 补齐模型注册、layer override、稀疏 draft logits、Gumbel selection 与 torch.topk fallback；DSpark 通过 config-only adapter 映射到 vLLM 的 Qwen3DSparkModel，权重保持原 checkpoint。FlashInfer JIT 所需的本机 libcuda.so、LIBRARY_PATH 与 Conda C++ runtime 均由启动脚本固化。

3. 评测方法

  1. 分别启动 vanilla、DFlash2 和 DSpark 服务；每个数据集、每种方法先发送不计时 warmup。
  2. 并发 8 矩阵对每种方法发送 414 个请求，最多生成 512 tokens。
  3. 并发 1 矩阵对每种方法发送 750 个请求，最多生成 2048 tokens。
  4. 逐请求记录 latency、TTFT、TPOT、completion tokens 与 speculative counter，再按方法和数据集聚合。

冷启动请求会触发 speculative 路径的 Triton JIT。未经 warmup 的第一次请求不能与原生路径直接比较，正式矩阵均排除了该成本。

6. 官方 Selector 候选树

6.1 对照与在线统计流程

该实验固定官方 target checkpoint Qwen3.8-27B 和官方 draft checkpoint Qwen3.8-27B-DFlash2。base 行直接运行 vLLM 官方 DFlash2：candidate selector 计算 edge scores，官方 _selector_walk_kernel 逐 slot 取 edge-score argmax，得到 7-token 主干并执行标准线性 speculative verification。ours 从同一份 edge scores 出发，完整保留官方主干，再在 max_nodes=21、max_branching=2 预算内扩展 prefix-closed 候选树。

评测取 GSM8K JSONL 前 32 条，每条最多生成 2048 tokens；temperature=0、thinking off、concurrency 1，正式请求前运行 1 条 128-token warmup。在线服务在 scheduler 确认提交输出后，按 request ID 记录 verification steps 和 accepted draft tokens。每条请求先计算 tau_i = 1 + accepted_i / steps_i，表中均值再对 32 个请求等权平均。离线 selector trace 用于核对 edge score、主干与 tree metadata；正式 tau 来自完整在线 draft → target verify → cache update → scheduler commit 链路。

6.2 Tree target 数据流

  1. 官方 DFlash2 drafter 并行产生 7 个 proposal slot 的 hidden states、top-k candidates 与 unary logits，官方 selector 输出 [slot, predecessor rank, successor rank] edge scores。
  2. ours builder 先执行与官方 kernel 完全一致的 argmax walk并保护这条 trunk，再按累计路径概率扩展其余节点；单路径 sanity 已验证 2570 次 selector 调用全部一致。
  3. target runner 保存本轮全部 GDN speculative states 与 full-attention query KV blocks。每条 leaf replay 前恢复同一快照，并为 Qwen3.8 重新构建对应 token 的 inputs_embeds。
  4. 每条 leaf 运行标准 speculative chain；公共前缀 prediction 跨 leaf 必须一致。runner 选择 target 匹配最长的 leaf，恢复 cache 后重放所选路径，提交 accepted path 与 bonus token。
  5. scheduler 回退未接受 slot并记录已提交计数；分析器按 request ID 对齐 official、ours request trace 与 tree replay trace。

reference backend 每个 verification step 执行 leaf_count + 1 次 target forward；本次正式 tree 共 14635 次 target forward，平均每 step 6.7287 次。该版本用于验证多分枝 tau 与 lossless 输出，wall time 与吞吐不进入 speedup 对照。性能版本将把 ancestor mask 与 GDN parent-state gather 合并到一次 flattened tree forward。

6.3 计数验收

早期 HTTP 前后读取 Prometheus counter 的方法会把异步更新归入相邻请求；GPU runner trace 还会看到 scheduler 随后丢弃的 stale frame。最终版本把 request trace 放在 scheduler 的提交点，得到 official 的 2482/12352 与 tree 的 2175/12659，并与 Prometheus 批量总计严格一致。tree replay trace 按 request ID 和 committed step 数筛选后同样得到 2175 steps、12659 accepted，正式目录带 SUCCESS。

7. 结论与限制

  1. Qwen3.8-27B 的 DFlash2 和 DSpark 可在单张 A100 80GB 上通过固定 vLLM/CUDA 12.9 组合运行。
  2. 两种方法在并发 1/8 都加速原生服务，DFlash2 因 acceptance 更高而稳定领先 DSpark。
  3. 官方 selector 驱动的 ours tree 已跑通完整 vLLM draft、target verify、cache update 与 scheduler commit 链路；32 请求 mean tau 提升 12.84%，输出保持一致。
  4. tree 当前是多次 leaf replay 的正确性 reference；一次 target forward 的性能后端完成后再报告 latency 与吞吐。
  5. 2026-08 的兼容性实验早于当前 clean-gate 规范；2026-09 tree 实验具备初始、正式运行前 clean manifest、精确代码 commit 与失败结果标记。
